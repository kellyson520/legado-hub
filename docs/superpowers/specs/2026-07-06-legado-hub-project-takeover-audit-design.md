## 一、背景与目标

当前 `C:\Users\lihuo\Desktop\legado-hub` 是一份 **本地开发副本**，不是 Git 仓库根目录，当前不具备提交历史与分支上下文。项目表面结构完整，包含：

- `frontend/`：React + Vite 前端

- `docs/`：README、架构说明、代码指南，以及已有 superpowers 文档

用户希望我正式接手该项目，并完成以下工作：

1. **架构审计**：确认文档中的 DDD/模块设计是否真实落地
2. **工程审计**：确认项目在 Windows 本机、不使用 Docker 的情况下是否能跑通
3. **代码审计**：识别重复逻辑、失配文档、潜在 Bug、死代码与测试缺口
4. **安全审计**：检查默认密钥、接口暴露、鉴权接入、CORS、调试配置等风险
5. **运行验证**：前后端都要跑通，至少验证关键页面与关键 API
6. **输出物**：完整接手报告、高优先级问题榜单、后续整改建议；若发现明显问题，先汇报再修改

本次工作的目标不是直接做大规模重构，而是建立对项目的可信接手认知，并形成可执行的修复优先级。

## 三、备选接手方案

### 方案 A：纯静态全量审计

仅分析代码、配置、目录和文档，不运行前后端。

**优点**
- 快
- 风险低
- 不受本机环境影响

**缺点**
- 发现不了启动链路问题
- 无法确认前后端真实联调状态
- 工程问题与文档/配置偏差可能被低估

### 方案 B：静态审计 + 本机跑通验证 + 分阶段汇报（推荐）

先完成架构/工程/代码/安全静态审计，再基于 SQLite 本机运行前后端，最后汇总问题、风险和修复候选。

**优点**
- 同时覆盖设计层问题与真实可运行性问题
- 能验证“文档写了什么”和“系统真正能做什么”之间的差距
- 最符合“项目接手”场景

**缺点**
- 耗时高于纯静态审计
- 需要处理本机依赖与启动差异

### 方案 C：先跑通，再倒推审计

优先让前后端快速启动，再回头补看架构、工程和代码质量。

**优点**
- 能最快得到一个可操作环境

**缺点**
- 容易被局部环境问题牵着走
- 先修表面问题，后续可能返工
- 对“正式接手”来说信息不够系统

### 推荐结论

采用 **方案 B：静态审计 + 本机跑通验证 + 分阶段汇报**。

原因：本次任务不是单点 Bug 修复，而是完整接手项目。必须先建立结构理解，再用运行验证给结论兜底，最终形成可信的问题分级和整改路径。

## 四、审计设计

### 4.1 总体执行框架

接手工作分为四条主线：

1. **架构审计**
   - 对照 `README.md`、`docs/ARCHITECTURE.md` 与实际代码目录
   - 判断 DDD 分层是否真实落地
   - 识别模块边界、依赖方向、穿层调用与职责漂移

2. **工程审计**
   - 检查 frontend / backend 的依赖、配置、启动脚本、构建链路
   - 在 Windows 本机、SQLite 文件库条件下验证可运行性
   - 识别 Docker 假设与本机启动现实之间的落差

3. **代码审计**
   - 检查文档实现一致性、重复代码、死代码、异常处理缺口、测试覆盖盲区
   - 特别关注“文档宣称存在但代码未接入”的能力

4. **安全审计**
   - 检查默认密钥、CORS、DEBUG、鉴权中间件、敏感接口暴露、可选能力误暴露等风险
   - 输出高/中/低分级及环境适用性说明

### 4.2 执行顺序

采用 **先静态、后运行、再汇总** 的顺序：

#### 阶段 A：静态结构审计
- 读取：`README.md`、`docs/ARCHITECTURE.md`、`docs/CODE_GUIDE.md`
- 对照：`backend/app`、`frontend/src`、`nginx/`、`docker-compose.yml`
- 重点：
  - 文档声明的架构
  - 实际代码结构
  - 路由注册与功能启用情况
  - v0 / v1 能力是否真实接入

#### 阶段 B：工程可运行性审计
- 后端：
  - 检查 Python 版本、依赖安装、配置加载、启动入口
  - 在 SQLite 条件下完成启动验证
- 前端：
  - 检查 Node 依赖、Vite 构建、开发服务器启动、API 地址配置
- 联调：
  - 验证首页可访问
  - 验证至少一条关键 API 可用
  - 验证前端不是“只有页面可开、实际不可操作”

#### 阶段 C：代码质量与安全审计
- 后端重点：
  - 路由注册完整性
  - 配置读取逻辑
  - 中间件、异常处理、仓储工厂与实际实现一致性
  - 可选能力的降级行为
- 前端重点：
  - API 封装与调用路径
  - 页面路由与核心流程
  - 源码与构建产物关系
- 安全重点：
  - 默认 `SECRET_KEY`
  - 宽松 CORS
  - 文档/调试暴露
  - 鉴权是否仅存在于代码而未真正启用
  - 敏感能力是否缺少保护边界

#### 阶段 D：归纳输出与修复候选
- 汇总问题
- 按风险级别排序
- 标注是否影响：架构可信度 / 启动可用性 / 安全边界 / 后续开发成本
- 单独列出“可快速修复但需先确认”的候选项

## 五、交付结构

本轮接手审计完成后，输出四类结果：

### 5.1 完整接手审计报告
至少包含：

- 架构审计结论
- 工程审计结论
- 代码审计结论
- 安全审计结论
- 风险等级
- 每项问题的证据与建议

### 5.2 高优先级问题榜单
输出最值得立即处理的问题，包含：

- 问题描述
- 影响范围
- 风险级别
- 建议优先级
- 是否建议立即修复

### 5.3 运行结论
明确说明：

- 前端是否跑通
- 后端是否跑通
- 联调是否跑通
- 若未跑通，卡在哪一层

### 5.4 修复候选清单
对“明显高风险”或“低风险高收益”的问题：

- 单独列出
- 先向用户确认
- 经确认后再实施修复

## 六、证据标准

每个结论尽量附带以下一种或多种证据：

- 文件路径
- 关键代码位置
- 启动日志或报错栈
- 构建/测试输出
- 实际接口访问结果
- 页面访问或联调结果

原则：**没有证据的结论不进入最终高优先级榜单。**

## 七、风险与边界说明

### 7.1 当前已观察到的接手风险

基于预读，已有若干值得重点验证的风险信号：

- 根目录不是 Git 仓库，缺少提交历史与分支上下文
- README / 架构文档内容可能与当前代码启用状态存在偏差
- 后端存在 v1 接口模块，但主入口中有注释掉的注册逻辑，需验证“能力是否仅停留在代码层”
- Docker 场景下的 Redis / MinIO / 路径设定，可能与本机 SQLite 启动路径不一致
- 根路由返回 `/app/frontend/index.html`，在本机非容器环境下可能不可直接成立，需重点验证

### 7.2 本轮不主动做的事

除非用户确认，不主动进行以下动作：

- 大规模重构
- 无确认的安全策略重写
- 无确认的依赖升级
- 直接修复所有发现的问题
- 以 Docker 作为本轮唯一运行方式

---

## 八、成功标准

本轮接手工作完成的判断标准为：

1. 能说明项目的实际架构，而非仅复述文档
2. 能说明本机 SQLite 条件下前后端是否可运行
3. 能指出最关键的问题及其证据
4. 能区分“设计问题”“工程问题”“实现问题”“安全问题”
5. 能给出明确的后续修复优先级
6. 对可快速修复的问题，先形成确认清单，不越权直接修改
