# Provider 路由、模型发现与容错设计

## 目标

将系统设置页从单一 LLM 配置升级为可管理多个 OpenAI-compatible Provider 的控制台。管理员可以发现模型、编辑已有渠道，并为通用、AI 分析、写源 Agent、翻译和小说分析配置各自的主备“渠道 + 模型”队列。保存后，页面必须立即反映新的配置和 Agent 可用状态，无需刷新。

## 范围

本次包含：

- 多个 Provider 渠道的新增、编辑、启用和停用；
- 服务端携带已保存密钥请求 Provider 的兼容 `/models` 接口；
- 每个功能路由的有序渠道/模型组合；
- 对超时、连接失败、429、5xx、认证失败与模型不可用的跨渠道切换；
- 保存后前端状态刷新、密钥掩码和旧单渠道设置的兼容迁移。

不包含自定义 Provider 协议、按用户单独路由、自动成本优化、删除历史 Provider 或跨进程熔断器。

## 数据模型

### Provider 渠道

复用 `provider_accounts`，每个渠道保存：名称、OpenAI-compatible Base URL、API Key、默认模型和启用状态。API Key 仅在写入时出现于请求体，不会从任何读取或错误接口回传；列表和编辑视图只返回 `api_key_configured` 以及安全的掩码状态。

### 功能路由

新增持久化路由记录。每个记录包含功能组、Provider 账户 ID、该渠道在此功能中使用的模型、启用状态和整数优先级。允许的功能组固定为：

- `default`（通用）
- `ai`（AI 分析）
- `source_build`（写源 Agent）
- `translation`（翻译）
- `novel`（小说分析）

一个功能组的优先级从小到大依次尝试。每个组至少应有一个启用条目；空组将产生明确的“未配置路由”错误，而非使用不相关的 Provider。

## API 与运行时

- Provider 管理 API 支持列出、新增和编辑渠道；编辑时空 `api_key` 表示保留已有密钥。
- 模型发现 API 在服务器端以该渠道的密钥调用规范化后的 `/models`，返回去重、排序后的模型 ID。失败时返回脱敏错误；前端仍允许手动填写模型。
- 功能路由 API 读取和原子替换一个功能组的有序条目。
- 旧 `/system/llm-settings` API 保持可用，并映射到默认渠道和默认路由，保证旧客户端不受影响。
- Provider registry 从持久化路由构造每个功能组的有序候选项。服务调用不再硬编码 `gpt-4.1-mini`；没有明确模型的内部调用使用路由配置的模型。
- 外部调用显式提供模型时优先使用该模型以保持兼容性；若某 Provider 不支持该模型，则使用下一个路由条目自身的备用模型，并在结果中记录实际模型。
- 调用对网络/超时、429、5xx、鉴权失败和模型不可用执行切换；400/422 等请求无效错误不重复调用。全部失败时返回脱敏的逐次失败摘要。

## 设置页

页面替换单一 LLM 表单为两个区块：

1. **Provider 渠道**：新增、编辑、保存、启用/停用；“获取模型”按钮填充模型下拉框，无法发现时保留手动输入。
2. **功能路由**：分别展示五个功能组，可选渠道和模型，并用上移/下移调整主备顺序。

渠道保存后，前端会立即重新读取渠道、功能路由与写源 Agent 设置。并发请求采用版本保护，较早的加载结果不得覆盖较新的保存结果。密钥输入框在保存后清空，但页面立即显示“已配置”和掩码，绝不显示明文。

## 迁移与安全

启动时创建新路由表。已有 `openai_compatible` 账户且尚未有路由时，自动生成对应的默认路由和必要功能路由，保持现有单渠道调用可用。Provider 不直接删除，只允许停用，以免历史任务引用失效。

模型发现与运行时错误信息不得包含 Authorization 头、API Key 或 URL 查询中的敏感值。所有设置与模型发现接口继续受 `system.settings.manage` 权限保护。

## 验收与测试

- 保存渠道后，页面无需刷新即可更新渠道信息、掩码状态与写源 Agent 的 Provider 可用状态；
- 兼容 `/models` 成功时可选择模型，失败时可手动填写；
- 空密钥二次编辑保留已配置密钥；
- 五个功能组可选不同渠道和模型，并按明确优先级运行；
- 主渠道超时或返回可切换错误时使用备用渠道和备用模型；400/422 不进行切换；
- 所有渠道失败时响应与日志均不泄漏密钥；
- 旧 `/system/llm-settings` 的读取和更新行为保持兼容。
