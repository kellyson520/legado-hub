# LegadoHub 小说 Agent 一体化助手设计

日期：2026-07-21
状态：已获用户确认，待实施计划
范围：第一阶段以 Agent 核心为主，兼顾独立助手、书籍详情页和阅读器内助手三个入口

## 1. 目标与边界

LegadoHub 需要把现有小说 Agent、书源读取、小说理解、Provider 路由和前端 AI 能力整合成一个面向用户的小说助手。用户确认的目标包括：

- Agent 可从用户上传文件、已配置书源和网络链接读取小说内容。
- Agent 支持全文解析、章节摘要、人物与关系分析、事件时间线、情节检索、上下文问答、跨章节记忆、翻译和创作辅助。
- 用户可在独立助手、书籍详情页和阅读器内使用同一套 Agent 上下文。
- Provider API Key 由系统设置统一管理；用户只能选择系统开放的 Provider 和模型。
- 模型可按用户默认、书籍、会话和单次任务多层级选择。
- 上传内容持久化保存，支持继续阅读、提问和分析。
- 向量数据库、Embedding Provider 和 Agent 工具可配置。
- 缓存只允许同一用户复用，优先利用结构化知识、章节摘要和 Provider 前缀缓存来降低成本。
- 最大化复用现有代码，不新建平行小说模型、平行 Agent 注册表、平行 Provider 调用链或平行缓存接口。

“尽量不拒绝”定义为：对用户提供的正常小说内容尽量直接完成读取、分析、翻译和创作辅助，减少无意义的打断；仍然遵守模型供应商、版权、隐私、网络安全和系统权限边界，不通过提示词绕过上游安全限制。

本设计不把任意网络抓取、绕过站点访问限制、绕过 DRM 或跨用户共享内容作为目标。网络导入只处理用户有权访问且系统允许访问的内容。

## 2. 现有能力与复用边界

| 现有能力 | 复用方式 |
| --- | --- |
| `NovelAgent`、技能模块和 `ToolRegistry` | 继续作为 Agent 技能和工具的唯一注册体系，补充书籍上下文适配，不另建注册表 |
| `NovelBook`、`NovelChapter`、人物/关系/事件/状态实体 | 作为持久化小说知识的正式模型，扩展用户归属和索引元数据，不新建第二套 Book/Chapter 模型 |
| `NovelRepository`、`NovelIngestionService` | 作为书籍与章节的统一持久化和摄入边界 |
| `SourceReadService`、书源搜索/目录/正文接口 | 作为已配置书源读取适配器 |
| `AIConversationRepository`、`AIConversationMessage` | 保存用户级 Agent 会话和消息，扩展书籍、入口和模型选择信息 |
| `NovelAnalysisTask`、现有任务/调度设施 | 承载后台分析、索引构建、断点续跑和重试 |
| `AgentRuntimeService` | 继续记录 Agent Run、工具调用、结果和证据 |
| `ProviderPlatformService`、`ProviderRegistry`、`OpenAICompatibleProvider` | 作为所有聊天、提取、总结和 Embedding 调用的唯一 Provider 边界 |
| `CacheProvider`、Redis 和内存降级 | 作为热缓存、计数和降级缓存的统一接口 |
| `BM25Index`、`EmbeddingAdapter`、`RAGRetriever` | 扩展为 BM25、向量和知识图谱的混合检索，不重写成另一套 RAG |
| `AutoExtractor`、章节映射、小说理解服务和 Agent 技能 | 复用本地规则提取、摘要、实体、关系和事件能力 |
| 现有 `/api/v1/novel-agent/chat` | 保持兼容，内部转发到统一会话服务 |
| 现有 `AIWorkspacePage`、系统 Provider 配置和运维页面 | 扩展为模型/工具/向量配置和 Agent 入口，不创建平行设置页 |

现有 `NovelIngestion` 作为摄入过程记录保留，但必须关联正式 `NovelBook`。现有 `NovelAnalysisTask` 作为分析过程记录保留。二者都不能继续承担第二套书籍内容存储职责。

本文统一使用 `owner_scope` 表示当前认证主体的隔离范围：普通登录请求使用用户身份，API Key 请求使用现有租户/API Key 身份映射。所有仓储和缓存方法都必须显式接收 `owner_scope`，不提供省略隔离范围的默认查询。

## 3. 总体架构

```text
用户上传 / 书源 / 网络链接
          │
          ▼
现有读取与摄入适配器
          │
          ▼
NovelIngestionService
          │
          ▼
NovelBook / NovelChapter（按用户归属）
          │
          ├── 本地规则提取
          ├── LLM 结构化提取
          ├── BM25 索引
          ├── VectorStore 索引
          └── 人物/关系/事件/状态知识库
          │
          ▼
统一 NovelAgentAppService
          │
          ├── 独立助手
          ├── 书籍详情页助手
          └── 阅读器内助手
          │
          ├── AIConversationRepository
          ├── AgentRuntimeService
          ├── ProviderPlatformService
          └── 用户隔离缓存
```

统一 Agent 服务负责上下文编排，不负责重复实现抓取、向量数据库或 Provider 协议。每个入口只提供不同的上下文范围：独立助手可以跨章节，书籍页默认绑定整本书，阅读器默认绑定当前章节和阅读进度。

## 4. 数据模型与用户隔离

### 4.1 正式小说模型

以现有 `NovelBook` 和 `NovelChapter` 为正式内容模型。需要进行兼容性扩展：

- `NovelBook` 增加 `owner_scope` 归属字段，所有列表、查询、更新和删除都按归属过滤。
- `NovelChapter` 通过 `book_id` 继承书籍归属，不允许脱离书籍单独跨用户查询。
- `NovelIngestion` 增加 `book_id` 和 `owner_scope`，表示一次导入或更新过程。
- `NovelAnalysisTask` 增加书籍关联、`owner_scope`、索引版本和阶段状态信息，支持增量分析。
- `AIConversation` 增加 `book_id`、`entrypoint`、模型选择和上下文范围信息。
- `AIConversationMessage` 保持现有消息结构，工具调用和证据继续复用现有字段。

### 4.2 索引元数据

增加轻量的 `NovelIndexState` 索引状态记录；它不复制章节正文，只用于记录：

- 书籍知识版本
- 章节内容指纹
- 提取阶段状态
- BM25 构建状态
- 向量索引状态
- 使用的 Embedding 模型和维度
- 最后成功时间与失败原因

这类记录只负责增量判断和恢复，不替代 `NovelChapter`、实体、关系和事件仓储。

### 4.3 隔离规则

所有书籍、上传文件、会话、消息、阅读进度、知识查询和缓存键都必须包含当前 `owner_scope`。管理员查询需要显式使用管理员接口，不能依靠省略过滤条件来扩大可见范围。

## 5. 统一导入链路

三类输入统一转换为 `NovelBook` 和 `NovelChapter`：

```text
上传文件 ─┐
书源爬取 ─┼─> 内容标准化 -> 章节解析 -> 持久化 -> 分析/索引任务
网络链接 ─┘
```

### 5.1 上传文件

第一阶段支持 TXT、Markdown、HTML 和 EPUB。图片或扫描内容通过现有 OCR 能力进入同一章节解析链；PDF 等格式使用可插拔解析器，未配置依赖时返回明确的可安装/不可用状态，不影响其他格式。

上传处理要求：

- 文件大小、数量和用户存储配额检查。
- 文件名和 MIME 类型校验，禁止路径穿越。
- 内容哈希去重，避免重复存储和重复分析。
- 原始文件与标准化文本分开保存。
- 解析失败保留任务记录和错误原因，允许重试。

### 5.2 已配置书源

复用 `SourceReadService` 的搜索、目录和正文能力。书源导入只负责把来源结果映射为标准书籍/章节，不复制书源解析规则。多源内容继续使用现有的来源路由和章节互补能力。

### 5.3 网络链接

网络链接使用现有 Fetcher/读取基础设施，并增加安全边界：

- 只允许 HTTP/HTTPS。
- 阻止内网、回环、云元数据等地址。
- 限制响应大小、重定向次数、超时和并发。
- 清洗 HTML，保留标题、作者、章节和正文。
- 使用 URL 与内容指纹做幂等更新。
- 网络内容作为不可信数据输入，不能被当成 Agent 系统指令执行。

## 6. Agent 上下文、记忆与模型选择

### 6.1 记忆层级

1. 书籍知识记忆：人物、别名、关系、事件、状态、摘要、世界观和索引。
2. 用户阅读记忆：阅读进度、最近章节、标注、纠正和偏好。
3. Agent 会话记忆：消息、对话摘要、已确认事实和任务上下文。
4. 当前请求上下文：问题、检索结果、必要原文和工具结果，用完释放。

每次请求只加载当前用户、当前书籍和必要章节，不跨用户或跨书籍混用记忆。

### 6.2 模型覆盖优先级

```text
单次请求 > 当前会话 > 当前书籍 > 用户默认 > 系统路由默认
```

Provider API Key 只由系统设置保存和管理。用户可以选择管理员开放的 Provider/模型，但不能读取 API Key，也不能调用未开放的 Provider。

不同任务使用不同模型通道：保留现有 `novel` 作为兼容兜底组，并在现有 Provider 路由注册表中增加 `novel_chat`、`novel_extract`、`novel_summary` 和 `novel_embedding` 四个可选组。实现仍复用现有 Provider 路由机制，不在 Agent 内直接请求任何具体厂商。

### 6.3 三种入口

- 独立助手：用户选择书籍、模型和工具，可进行跨章节问答与分析。
- 书籍详情页：自动绑定书籍，展示分析状态、人物、关系、事件和摘要。
- 阅读器内助手：自动绑定当前用户、书籍、章节和进度，只加载相关上下文。

三种入口使用同一个 `AIConversation`，可以在页面之间继续同一段会话。

## 7. 向量检索与小说理解索引

### 7.1 可配置 VectorStore

在基础设施层定义统一的 `VectorStore` 端口，至少支持：

- 创建/检查集合
- 批量写入和更新向量
- 按用户、书籍、章节和版本过滤
- 相似度搜索
- 删除书籍或版本索引
- 健康检查和统计

向量后端由系统设置选择：关闭、内置本地实现、Qdrant 或 pgvector 等。具体适配器按依赖可选安装。外部向量库不可用时自动退回 BM25 和结构化知识检索。

`EmbeddingAdapter` 改为通过现有 Provider 配置解析 Embedding 模型和 API，不直接硬编码 API URL/Key。现有本地 Hash 向量只能作为无语义的降级标识，不得作为真实语义检索结果对外宣称。

### 7.2 增量提取流水线

```text
章节内容变化
    ↓
清洗、去重、章节指纹
    ↓
本地规则提取
    ├── 人物名称、别名、出现次数
    ├── 地点、势力、物品
    └── 基础统计
    ↓
LLM 结构化提取
    ├── 关系
    ├── 事件
    ├── 状态变化
    ├── 摘要
    └── 篇章/剧情线
    ↓
去重、合并、置信度校验
    ↓
更新现有实体仓储、BM25 和 VectorStore
```

本地规则优先，确定性内容不调用 LLM。LLM 输出必须经过结构化解析、字段校验、重复合并和证据章节绑定。

### 7.3 混合检索

扩展现有 `RAGRetriever` 的三轨策略：

- 精确人名、次数、关系：结构化知识库优先。
- 原句和关键词：BM25 优先。
- 相似情节：向量检索优先。
- 复杂问题：BM25、向量和知识图谱融合并重排。

返回结果必须带书名、章节号、来源类型、置信度和证据片段，便于 Agent 给出可追溯回答。

## 8. Agent 工具

继续复用现有 Tool Registry 和技能注册机制，工具按用户、书籍和权限动态暴露。需要补齐或统一以下能力：

- 章节检索
- 人物档案
- 人物出现次数和章节列表
- 别名查询
- 关系查询
- 事件时间线
- 状态变化
- 世界观查询
- 语义检索
- 原文证据读取
- 章节摘要
- 书籍统计
- 阅读进度读取

工具权限沿用现有 `read / propose / operate` 分类：读取和分析默认允许；修改书籍、删除内容、发布创作结果等操作需要确认。每次工具调用继续记录到 `AgentRuntimeService`。

## 9. DeepSeek 等 LLM 的缓存与成本优化

请求拆为稳定前缀和动态后缀：

```text
稳定前缀：系统规则 + Agent 身份 + 工具定义 + 书籍摘要 + 固定世界观
动态后缀：用户问题 + 阅读位置 + 检索结果 + 必要原文
```

### 9.1 热缓存

复用现有 `CacheProvider`、Redis 和内存降级。缓存键至少包含：

```text
prompt_version
user_scope
book_id
knowledge_version
model
task_type
query_hash
toolset_version
```

键中不直接写入完整原文或 API Key。缓存只允许同一用户复用；不做跨用户语义缓存。

### 9.2 缓存内容

- 章节清洗结果
- 章节摘要
- 人物和事件提取结果
- Embedding 结果
- 检索结果
- 用户级最终回答缓存

用户切换模型、书籍内容、Prompt、工具集或知识版本时，相关缓存自动失效。失败请求只做短时重试保护，不进入长期结果缓存。

### 9.3 上下文压缩

- 优先加载全书摘要、篇章摘要和人物状态。
- 只加载和问题相关的章节片段。
- 工具结果使用结构化摘要，不重复注入原始大 JSON。
- 长会话保留最近消息，旧消息压缩为带版本的会话摘要。
- 记录输入/输出 Token、Provider 缓存命中信息和估算费用。

## 10. API 与兼容性

继续扩展 `/api/v1/novel-agent`，避免新增平行接口体系。接口职责包括：

- 小说上传、导入和更新
- 书籍列表、详情和上下文
- 会话创建、消息发送和流式响应
- 后台分析与索引任务
- 人物、关系、事件、摘要和证据查询
- Agent 工具查询和调用
- 当前用户可选模型查询

现有 `/api/v1/novel-agent/chat` 保留兼容，内部转发到统一会话服务。现有书源阅读、小说分析和 AI Workspace API 不直接删除，逐步改为调用统一应用服务。

## 11. 系统配置

在现有 Provider/System Settings 基础上增加：

- 小说聊天、提取、总结和 Embedding 的路由。
- Provider 可用模型和用户可见模型。
- 向量后端、地址、凭据、集合前缀和维度。
- Embedding 模型和批量参数。
- Agent 工具启用/禁用和权限分类。
- 章节大小、并发、重试、索引构建策略。
- 用户缓存 TTL、语义阈值和成本预算。
- 当前连接状态、索引状态和缓存命中统计。

凭据只保存服务端，前端只显示配置状态和脱敏信息。

## 12. 失败处理与安全

- 向量库不可用：BM25 + 结构化检索降级。
- Embedding 不可用：跳过向量索引，不伪装为语义检索。
- LLM 不可用：继续提供阅读、关键词搜索、人物统计和已有分析。
- 单章解析失败：记录失败原因，其他章节继续处理。
- Provider 失败：使用现有路由和备用模型策略。
- 新章节只做增量处理，支持断点续跑。
- 上传文件限制大小、格式、数量和存储配额。
- 网络解析限制协议、重定向、响应大小、超时、并发和目标地址。
- 小说正文作为不可信数据，不能覆盖 Agent 系统规则或触发未授权工具。
- 所有读取、工具调用、模型调用和资源访问按用户/租户隔离并记录审计。

## 13. 分阶段实施

### 阶段一：统一 Agent 核心

- 用户/书籍/章节/会话上下文统一。
- 上传、书源、网络链接进入统一摄入链。
- 模型选择和用户级缓存。
- 独立助手、书籍页、阅读器入口接入统一后端。
- 保留现有 API 兼容。

### 阶段二：小说理解索引

- 增量章节解析。
- 人物名称、别名、出现次数。
- 关系、事件和状态变化。
- BM25、向量和知识图谱混合检索。
- VectorStore 配置和重建。
- 后台任务、断点续跑和成本统计。

### 阶段三：配置和体验完善

- Provider/模型/Embedding/向量库系统设置。
- Agent 工具权限和开关。
- 用户模型选择界面。
- 三入口的上下文状态同步。
- 后续接入完整书架和原生阅读器体验。

## 14. 测试与验收

测试使用假的 Provider 和假的 VectorStore，不依赖真实 API Key；真实 Provider 只做独立验收。

### 单元测试

- 导入格式识别、文本清洗、章节切分和内容指纹。
- 模型选择优先级。
- 缓存键用户隔离和失效规则。
- 本地人物/别名/次数提取。
- 关系、事件和状态结构化校验。
- BM25、VectorStore 和知识图谱检索融合。
- 增量索引和断点恢复。

### API 与集成测试

- 上传、书源、网络链接三类导入。
- 会话创建、消息发送、流式响应和跨入口续接。
- 用户只能访问自己的书籍、消息、索引和缓存。
- Provider 选择、失败重试和备用路由。
- 向量库关闭或异常时的降级。
- 旧 `/api/v1/novel-agent/chat` 和现有书源/小说接口无回归。

### 安全测试

- 路径穿越和恶意文件。
- SSRF、内网地址和云元数据访问。
- 跨用户数据访问。
- 小说内容中的 Prompt Injection。
- 未授权工具调用和敏感配置暴露。

### 用户验收

1. 用户上传小说后可以持久化保存并继续阅读。
2. 用户可以从书源或网络链接导入并继续分析。
3. 用户可以在全局、书籍、会话和单次任务选择模型。
4. 同一用户可以命中自己的缓存，不同用户不能命中。
5. Agent 可以回答人物次数、人物关系、事件时间线和章节证据问题。
6. 向量库可以配置、测试、禁用和切换。
7. 向量库关闭时，BM25 和结构化检索仍能工作。
8. 新章节只做增量分析。
9. 独立助手、书籍页和阅读器内助手共享会话上下文。
10. Provider、工具调用、Token、成本和缓存命中可审计。

## 15. 本轮绑定修复与性能增量设计

本轮优先处理已经在线复现的两个问题：书籍会话没有真正使用统一 NovelAgent，以及上传后的分析任务没有处理无编号章节。

### 15.1 已确认根因

1. `AIWorkspaceService` 的生产装配没有注入 `NovelAgentAppService`。书籍会话虽然已经在 `ai_conversations.book_id` 和消息中保存了 `book_id=8`，但 `/api/ai` 仍调用旧的通用 AI Provider；旧链路不会读取 `NovelBook`、章节或 RAG 证据，因此会反问“哪本书”。
2. 上传文件被解析为单个无编号章节，章节的 `canonical_num` 为 `0`。`NovelIndexService` 初始查询使用 `canonical_num >= 1`，导致任务结果为“成功、处理 0 章”，书籍停留在 `summarizing / 0.3`，实体、事件和关系均不会生成。
3. 统一小说 Agent 和 `RAGRetriever` 当前按请求重新创建，BM25 索引和 Agent 级缓存无法跨请求复用，增加了首次检索和配置装配开销。

### 15.2 修复方案

#### A. 绑定会话统一走 NovelAgent

- 在 AI Workspace 的 HTTP 依赖层装配现有统一 `NovelAgentAppService`，复用现有小说仓储、RAGRetriever、Provider 路由、会话仓储和缓存。
- 创建或发送带 `book_id`、`book`/`reader` 入口的会话时，优先委托统一 NovelAgent；已经绑定书籍的会话即使单次请求省略 `book_id`，也从持久化会话继承。
- 没有绑定书籍的旧通用工作台会话继续使用原有 `AIWorkspaceService`，保留书源工具等兼容能力。
- Agent 上下文必须至少包含书籍公开元数据、当前阅读进度、当前章节（若有）和检索证据；不把正文当作系统指令。

#### B. 修复无编号章节并正确结束任务

- 初次索引允许从 `canonical_num=0` 开始；显式章节范围也允许 `0`，不改变正常从第 1 章开始的书籍。
- “无章节”不再被静默当成成功；任务结果必须区分无数据、成功和失败，并保留原因。
- 索引任务成功后把对应书籍更新为 `ready / 1.0`；部分失败继续保留可读状态和可重试状态，并保存失败章节信息。
- 保留现有内容指纹和 `NovelIndexState` 增量判断，重复运行不重新处理未变化章节。

#### C. 降低分析与问答等待时间

- 对同一进程复用统一小说 Agent、RAGRetriever 和 BM25 索引；模型路由变化只刷新 Provider 选择，不丢弃章节索引。
- 小说分析中的本地规则提取保持无 LLM 优先；只有确实启用结构化 LLM 提取、摘要或 Embedding 时才发起对应 Provider 请求。
- 持久化层优先使用现有批量保存接口，减少每个实体/关系一次提交造成的 SQLite 往返；单章失败仍可隔离。
- 保留现有用户级答案缓存，缓存命中不重复调用 Provider；缓存键继续包含用户、书籍、知识版本、模型、任务类型、问题和工具集版本。
- 不用盲目增加并发来掩盖 SQLite 写入瓶颈；先测量章节提取、持久化、Embedding 和 Provider 各阶段耗时，再按阶段优化。

### 15.3 回归与性能验收

必须新增或补充以下测试：

- 绑定 `book_id` 的 `/api/ai` 会话将书籍上下文传递给统一 NovelAgent；未绑定的旧会话仍走兼容链路。
- 持久化会话省略单次 `book_id` 时，Agent 仍使用会话绑定的书籍，不发起“请提供书名”的泛化上下文。
- `canonical_num=0` 的单章上传书能被索引，任务至少处理 1 章，并将书籍状态更新为 `ready`。
- 索引重复运行会跳过内容未变化章节；无章节任务不会被伪装成成功。
- Agent/RAG 服务在同一进程内复用，重复请求能保留 BM25 索引和答案缓存，且不同用户缓存隔离。
- 运行真实书籍 8 的一次索引验收，确认 `novel_index_states`、人物/事件/关系和书籍状态发生预期变化；不以“HTTP 200”代替分析完成。
