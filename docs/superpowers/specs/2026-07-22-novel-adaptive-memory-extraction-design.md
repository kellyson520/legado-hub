# 小说自适应知识库、记忆检索与 Agent 裁决设计

## 1. 背景

当前小说理解链路已经具备实体、关系、事件、状态变化、BM25、向量检索和小说 Agent 基础，但底层提取仍存在几个会直接影响问答质量的问题：

- 上传章节可能使用 `canonical_num=0`，被索引查询的 `canonical_num >= 1` 条件排除。
- 人物候选主要依赖连续中文片段和常见姓氏，容易生成“江轩很”“江轩便”“周围的”等伪人物。
- 关系兜底逻辑会把低质量候选两两组合，造成关系数量膨胀且缺少正文证据。
- 结构化结果落库后没有可靠回填书籍统计。
- 当前向量记录主要代表章节，人物、物品、事件和状态变化没有形成可直接召回的记忆卡。
- Agent 可以读取小说上下文，但缺少足够细粒度、带证据的知识工具；如果全量交给 Agent，延迟和成本都不可接受。

本设计先增强本地算法，再将少量无法确定的候选交给 Agent；最终形成可恢复、可解释、可增量学习的单用户小说知识库。

## 2. 目标与边界

### 目标

1. 让已上传小说和后续新小说都能稳定完成实体、关系、事件、状态和记忆索引。
2. 将人物、物品、地点、势力、境界、技能、设定、生物等相关信息统一纳入书籍知识库。
3. 本地算法处理绝大多数内容，Agent 只处理明确的歧义和冲突。
4. 每条重要知识都保留章节、正文证据、置信度和处理版本。
5. 支持 BM25、向量和知识图谱混合检索，供 Agent 快速回答问题。
6. 使用 Agent 的结构化裁决和用户明确纠正，受控地改进词表、别名和特征权重。
7. 保持索引任务可恢复、幂等，避免重复分析和重复计费。

### 边界

- 不把整本小说无条件发送给 LLM。
- 不允许 Agent 自行修改程序代码、系统提示词或任意覆盖已有事实。
- 不直接复制外部酒馆插件代码；只借鉴触发词、重要度、时效性和分层记忆的设计思想。
- 继续使用现有单用户 `owner_scope` 隔离，不扩展到多租户产品设计。

## 3. 总体架构

```text
章节正文
  -> 文本规范化与章节排序
  -> 本地候选提取与特征评分
  -> 实体、关系、事件、状态结构化落库
  -> 证据片段与记忆卡生成
  -> BM25 + 向量 + 知识图谱索引
  -> Agent 按问题调用细粒度工具
  -> 仅对低置信度候选进行批量裁决
  -> 裁决/纠正形成受控学习信号
```

现有 `NovelEntity`、`NovelRelationship`、`NovelEvent`、`NovelStateChange`、`NovelIndexService`、`BM25Index`、`RAGRetriever` 和 `VectorStore` 继续作为核心边界。新增能力通过现有接口扩展，避免再造一套并行知识库。

## 4. 本地提取算法

### 4.1 章节输入与规范化

- `canonical_num=0` 的序章、前言、未解析章节和番外仍然参与索引。
- 章节排序优先使用规范化序号和原始顺序，无法解析时使用数据库章节 ID 保证稳定顺序。
- `from_chapter` 对规范化序号和原始顺序分别处理，不能因为序号缺失而丢弃正文。
- 正文先做 HTML/控制字符清理、标点统一、段落和句子切分，并保留原文偏移映射，保证证据可以回指原文。

### 4.2 候选生成

人物、物品和其他实体使用多来源候选，不再将“常见姓氏 + 2～3 个汉字”作为硬门槛：

- 明确命名句：叫作、名为、自称、原名、姓、封号、又称等。
- 对话归属和动作上下文：说、问、答、看、走、出手、拿取、使用等。
- 称谓和名称邻近：姑娘、公子、师兄、殿下、夫人、前辈、掌门等。
- 被其他角色称呼、跨句重复出现、章节标题或角色介绍中的名称。
- 物品动作和状态：获得、取出、佩戴、握住、使用、炼制、赠予、转移、损坏、升级等。
- 地点、势力、境界和概念继续复用已有类型；技能、功法、规则、生物等使用现有类型加 `attributes.subtype`，只有现有类型无法表达时才扩展枚举。

每个候选生成一条内部证据记录，至少包括名称、类型、章节 ID、正文偏移、证据片段、出现次数、命中特征和负向特征。

### 4.3 评分与过滤

评分由明确命名、行为归属、称谓邻近、跨句重复、跨章节出现、实体类型线索、常见词冲突等特征组成。常见姓氏只加分，不作为硬条件。

- 高置信度候选直接持久化。
- 中间置信度候选进入待裁决队列。
- 低于候选下限且缺少有效证据的片段直接丢弃。
- 常见功能词、动词残片、形容词残片、身体部位和模板化短语进入负向词表。
- 统计出现次数时使用候选位置结果，避免对每个候选重复扫描整章。

别名采用保守合并：只有“又称、原名、自称、改名”等明确证据，或多个章节存在稳定共现证据时才自动合并；不因字符串相似就强行合并。

### 4.4 关系、事件和状态

- 关系必须来自同一句、相邻句或明确段落的证据窗口。
- 模式必须能解析出关系两端；不再对章节内所有候选做笛卡尔积。
- 亲属、师徒、敌对、合作、从属、占有和自定义关系保留方向语义；对称关系使用稳定的去重键。
- “美女、倾国倾城、关系密切”等泛化描述不能单独推出恋爱或亲属关系。
- 事件和状态变化记录触发句、参与实体、发生章节和前后状态；物品获得、转移、使用、损坏和归属变化进入状态轨迹。
- 结构化结果保存证据和置信度；证据不足时保存候选状态，不伪造确定事实。

## 5. 分层记忆与向量库

书籍记忆分为四层：

1. 原文证据：章节片段、标题、章节号、偏移和内容哈希。
2. 实体记忆卡：人物、物品、地点、势力、境界、技能和设定的名称、别名、属性、出场范围、描述和证据摘要。
3. 事件/状态记忆：事件时间线、角色关系变化、物品流转和角色属性变化。
4. 检索索引：BM25 倒排、向量记录和知识图谱查询。

向量记录通过现有 `VectorRecord`/`VectorStore` 扩展 payload，增加 `memory_type`、`entity_id`、`event_id`、`trigger_keys`、`importance`、`chapter_start`、`chapter_end`、`content_hash` 等元数据。章节向量继续保留，新增实体卡、事件卡和证据卡只在内容变化时增量向量化。

检索采用关键词、BM25、向量和知识图谱混合排序，叠加实体别名命中、重要度、当前章节距离、证据置信度和时间范围。重复内容使用哈希去重，Embedding 失败时仍能使用 BM25 和结构化知识。

## 6. Agent 裁决与底层工具

### 6.1 裁决边界

`NovelIndexService` 通过可选的 adjudicator 接口调用现有小说分析流水线/模型路由，不把 Agent 实现硬编码进规则提取器。候选按书籍和章节批量提交，证据包只包含必要的句子或段落。

Agent 只能对候选返回接受、拒绝、合并、拆分或暂存，并且必须引用证据编号。超时、模型不可用或 JSON 无法校验时采用本地结果并保留待裁决状态。

裁决缓存键包含 owner、book、正文哈希、候选集哈希、算法版本和提示版本，避免重复调用。

### 6.2 只读小说工具

复用现有 Agent 工具授权和调用边界，增加以下只读能力：

- `novel.search_memory`
- `novel.get_entity_profile`
- `novel.get_mentions`
- `novel.get_relations`
- `novel.timeline`
- `novel.get_item_state`
- `novel.compare_entities`
- `novel.get_chapter_evidence`
- `novel.index_status`

工具返回结构化数据、证据片段、章节号、置信度和来源版本。`queue_rebuild` 等维护动作只供内部任务或管理员使用，不由普通对话任意触发。

## 7. 受控自主学习

自主学习指本地知识和参数的增量适配，不是让模型修改代码。每本书维护版本化 learning profile，包括：

- 已确认别名和称谓映射。
- 已确认的物品/技能/设定词。
- 多次证实的正向模式和误报排除词。
- 有界的特征权重和实体类型先验。
- Agent 裁决记录、来源证据和更新时间。

学习信号只来自高置信度规则结果、证据充分的结构化 Agent 裁决和用户明确纠正。普通自由聊天回答不直接进入学习集。更新需要达到重复证据或明确命名条件，参数变化有上下限、版本和回滚记录；不同书籍默认隔离，避免词义互相污染。

系统持续记录本地通过率、Agent 调用比例、待裁决数量、重复裁决命中率、向量命中率和估算 Token 成本，用于调整阈值和批量大小。任何学习更新都不能阻塞主索引任务。

## 8. 索引任务、补跑和统计

- 新上传书籍自动创建索引任务。
- 调度器扫描无索引状态、失败状态、统计为零但正文存在、版本过期的书籍并自动补建任务。
- 章节按正文哈希、知识版本、Embedding 模型和维度幂等跳过。
- 单章失败不影响其他章节，任务支持续跑。
- 实体、事件、关系和状态落库后重新计算书籍统计，并按实体类型维护可扩展统计。
- 算法或记忆版本变更触发增量重建，不删除仍可用的旧证据。

## 9. 前端和时间规范

- Agent 回复使用安全的 Markdown/GFM 渲染，支持表格、列表、引用、代码块和链接。
- 工具结果按数据类型显示为表格、标签或折叠证据卡，复杂结构回退为格式化 JSON。
- 用户消息、Agent 消息、工具调用、授权和失败状态使用清晰的视觉层级。
- 后端新写入时间统一为带 UTC 时区的 ISO 8601；历史无时区数据按既有 UTC 语义兼容。
- 前端统一解析时间，按浏览器本地时区显示完整时间和相对时间，避免裸字符串造成时差。

## 10. 实施顺序

1. 先修章节纳入、候选提取、关系证据约束、统计回填和自动补跑。
2. 接入物品/技能/设定等实体记忆卡、事件状态记忆和增量向量索引。
3. 增加细粒度 Agent 工具和低置信度批量裁决。
4. 增加版本化反馈学习和成本/质量指标。
5. 完成 GFM 对话渲染和 UTC/本地时间显示。
6. 针对已上传小说执行回归索引，确认错误候选和统计结果明显改善。

## 11. 验收标准

- `canonical_num=0` 的上传章节可以被索引。
- 上传小说能够产生非零且合理的人物、实体、事件和关系统计。
- 伪人物和无证据关系显著减少，所有关系均可回指正文证据。
- 物品、技能、设定和状态变化可被结构化查询与向量检索召回。
- 普通索引不调用 Agent；只有待裁决候选触发批量 Agent 调用。
- Agent 失败不会导致整本书索引失败，缓存能避免重复计费。
- Agent 工具结果带证据、章节和置信度。
- 学习 profile 可版本化、回滚且不会被普通聊天内容污染。
- 前端能正确渲染 GFM 表格和代码块，时间显示不再发生时区错误。
- 后端、前端和针对上传小说的回归测试通过。
